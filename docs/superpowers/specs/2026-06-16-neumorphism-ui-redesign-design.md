# WindWalker 拟物化 UI 重设计方案

日期：2026-06-16
状态：对话内方案已确认，待最终文档复核
负责人：Codex

## 概述

WindWalker 将重设计为一套在浅色与深色主题下都保持统一的 Neumorphism（拟物化软 UI）风格应用。

本次已确认的视觉方向为：

- 基础风格：`B 功能平衡型`
- 实施范围：`C 页面级全面重写`

这意味着本次改造不会停留在局部换肤或单纯调整主题，而是以整套产品视觉一致性为目标，同时继续保证任务管理场景下的可读性、可扫描性和高频操作效率。

## 目标

- 为整个 App 建立一套统一的 Neumorphism 设计语言。
- 同时支持浅色和深色两套主题，并将二者作为一体化设计，而不是简单反相。
- 重绘核心页面，使不同页面在视觉气质和交互反馈上保持一致。
- 保留任务列表、状态信息、进度信息和关键操作的高可读性。
- 产出一份可复用的 UI 风格描述文件，用于后续 UI 生成和统一配色规范。

## 非目标

- 不调整路由结构、状态管理架构或下载器业务逻辑。
- 不改变现有信息架构和功能范围。
- 不完全脱离 Flutter `ThemeData` 另起一套渲染体系。
- 不追求对某个外部设计系统的像素级复刻。

## 产品约束

- App 的本质仍然是一个下载器管理工具，存在大量状态驱动的信息展示和操作。
- 视觉一致性不能以牺牲任务状态、进度、危险操作和活跃操作的辨识度为代价。
- 页面视觉结构可以重组，但功能行为需要保持稳定。
- 改造后的代码仍需适合后续 Flutter 持续维护和扩展。

## 设计方向

### 核心风格

本次采用“功能平衡型”的 Neumorphism 语言，核心特征为：

- 柔和的软表面背景
- 大圆角和统一几何语言
- 克制的外阴影，用于表达外凸表面
- 轻微的内阴影，用于表达内凹控件
- 低噪音、低饱和度的基础表面
- 对主操作、任务状态和危险操作保留更强对比

整体观感应当是安静、统一、细腻、有质感的，但仍然要保有工具型 App 的效率感，而不是做成偏展示型的概念界面。

### 选择该方向的原因

纯粹的柔光拟物风格虽然更“软”，但会明显削弱任务型页面的扫描效率。因此本次方向保留拟物层次感，但允许在以下场景中使用更明确的对比与强调：

- 主操作按钮
- 当前选中态
- 下载进度
- 错误与删除类操作
- 状态标签与状态徽标

## 主题系统

### 浅色主题

浅色主题采用雾灰蓝系软表面系统：

- 页面背景：偏雾感的浅灰蓝
- 外凸表面：比背景稍亮，通过高光和暗影拉开层次
- 内凹控件：略深的凹槽感表面，并带有柔和高光
- 主文本：深石板色
- 次文本：中低对比的石板灰
- 主强调色：保留 WindWalker 现有蓝色基因，但降低刺眼感

状态色继续保留语义一致性，但表达方式从“大片纯色块”改为更细腻的表达：

- 成功：青绿色
- 下载中 / 警告：暖琥珀色
- 错误：柔化的红色，但保证前景清晰
- 暂停 / 离线：偏蓝灰中性色

状态表达优先采用以下组合方式：

- 柔和底色
- 清晰标签文字
- 必要时的图标或强调条

而不是依赖高饱和实体块铺满整个区域。

### 深色主题

深色主题不采用浅色的简单反相，而是独立设计为深石墨 / 蓝灰黑软表面系统：

- 底层背景：深蓝黑
- 外凸卡片：比背景稍亮的石墨面
- 内凹控件：更深的凹槽，并配合轻微冷色高光
- 文本：高可读的冷白和灰蓝辅助文字
- 主强调色：与浅色保持同一品牌蓝，但亮度需针对深色对比做提升

深色拟物化需要特别避免“发糊”和“发脏”的问题。层次应主要来自：

- 相邻表面之间适度而明确的明度差
- 轻克制的冷光高光
- 低透明度、可叠加的柔和阴影

而不是使用过亮高光或过于松散的模糊阴影。

### 共享设计 Token

浅色与深色主题必须共享同一套 token 分类，确保它们是同一种视觉语言的两个版本，而不是两套互不相关的皮肤。

需要统一的 token 分类包括：

- 背景层级
- 表面层级
- 文本层级
- 语义状态色
- 阴影配方
- 高光配方
- 细边界 / 分隔色
- 圆角体系
- 间距体系
- 控件高度
- 图标尺寸
- 按压 / 悬停动效时长

这些 token 既要落在代码里，也要同步沉淀到 UI 风格描述文件中，便于后续 UI 生成和统一引用。

## 组件体系

本次重构不应继续依赖页面内分散的 `BoxDecoration` 自行拼装，而应建立统一的 Neumorphism 组件层。

计划引入的基础组件包括：

- `NeoSurface`：页面底板、分组容器、基础表面模型
- `NeoCard`：外凸卡片，用于任务、设置项、下载器信息块
- `NeoInput`：内凹输入框、搜索框、路径输入框
- `NeoButton`：主按钮、次按钮、弱化按钮、危险按钮
- `NeoChip`：筛选标签、分段选择控件
- `NeoBadge`：状态徽标与辅助元信息标签
- `NeoProgress`：进度条及其轨道 / 进度值表达
- `NeoSection`：具备标题、副标题、正文结构的内容分组
- `NeoActionBar`：底部固定操作区
- `NeoDialog`：确认、删除、设置相关弹窗

每个组件都必须定义：

- 浅色主题表现
- 深色主题表现
- 默认 / 悬停 / 按下 / 选中 / 禁用 状态
- 外凸 / 内凹时的阴影规则
- 所使用的圆角和间距约束

## 页面级重设计范围

本次改造是页面级全面重绘，而不是只改主题文件。

以下页面需要纳入统一重设计范围：

- `tasks_page.dart`
- `all_tasks_tab_page.dart`
- `add_task_page.dart`
- `downloader_config_page.dart`
- `downloader_editor_page.dart`
- `settings_page.dart`
- `about_page.dart`
- 与这些页面强相关的共享弹窗和复用组件

以下页面需要额外检查是否与新系统存在明显风格漂移，并在必要时同步调整：

- `task_detail_page.dart`
- `login_page.dart`
- `startup_page.dart`

## 页面重绘规则

### 任务列表页

任务相关页面在采用新风格时，仍要优先保证扫描效率。建议具备以下视觉结构：

- 柔和背景底板
- 内凹式搜索框
- 带托盘感的筛选区或分组筛选条
- 外凸任务卡片，并在卡片内部建立清晰层级
- 紧凑但不拥挤的元信息区
- 高识别度的进度和状态展示

任务卡片内部建议明确分出以下信息区块：

- 任务标题
- 下载器 / 来源信息
- 进度信息
- 传输速度与体积等指标
- 状态与操作区

目标是摆脱旧式平铺 ListTile 观感，但不牺牲可扫读性。

### 添加任务页

添加任务页应从“多个零散块状区域”重构为更统一、更完整的引导式页面。推荐结构为：

- 顶部页面引导信息
- 下载器选择区
- 链接 / Torrent 来源区
- 保存路径区
- 底部固定主操作区

每个区块应采用统一的外凸表面，而输入和选择器则使用内凹控件语言。

### 设置页与下载器配置页

设置与下载器配置页面应采用更清晰的分组结构：

- 分组 Section
- 外凸内容面板
- 内凹表单输入
- 明确区分保存操作和危险操作
- 更清晰的标签、说明、值控件层级

目标是让配置类页面与任务页同样属于一套产品语言，而不是风格游离的表单页面。

## 交互与反馈

Neumorphism 不能只停留在静态截图层面，交互反馈必须体现同一语言。

所有关键控件至少要覆盖以下状态：

- 默认
- 悬停
- 按下
- 选中
- 禁用

按压反馈应优先通过“深度变化”表达，而不是仅仅改颜色：

- 外凸表面在按下时产生轻微压入感
- 内凹控件在激活时产生更明显的深入感
- 高光与阴影分布随状态变化而重新平衡

颜色变化是辅助，不是唯一反馈来源。

## 数据、状态与错误表达

柔和的视觉风格不能模糊业务含义。需要遵守以下规则：

- 状态绝不能只靠阴影区分
- 进度必须保持快速可扫描
- 危险操作必须有足够清晰的识别方式
- 加载、空状态、错误状态要纳入同一套设计语言
- 深色主题下的状态辨识度不能低于浅色主题

重要状态建议结合多种信号共同表达：

- 颜色
- 文本标签
- 必要时的图标
- 固定位置
- 局部强调条或强调面

## 可用性与可访问性护栏

虽然目标风格是 Neumorphism，但必须避免该风格常见的可用性问题。约束如下：

- 文本与操作前景必须保有足够对比度
- 不能让所有表面看起来几乎一样
- 点击区域必须足够明确
- 当前选中态必须一眼可辨
- 表单焦点态在浅色和深色中都要清晰
- 状态色在柔化之后仍然要保持正确语义

## 技术实现说明

实现层面仍以 Flutter `ThemeData` 作为底层 token 提供者，但页面视觉不再依赖默认 Material 外观，而是由自定义的 Neumorphism 组件和页面骨架主导。

推荐的实现方向：

- 将 `AppTheme` 扩展为明确的浅色 / 深色拟物化 token 集
- 在 `lib/core/theme/` 或邻近的共享 UI 目录中建立基础组件原语
- 将页面中的局部硬编码 `BoxDecoration` 和颜色逐步迁移到统一组件
- 对现有 spacing / radius / elevation token 做统一重整，以贴合新体系

所有与新风格冲突的硬编码颜色、局部渐变和一次性阴影都应尽量移除或吸收到统一 token 中。

## UI 风格描述文件

本次改造必须产出一份可复用的风格描述文件，用于未来 UI 生成和统一配色参考。

固定产出路径：

- `docs/design/neumorphism-style-guide.md`

该文件至少应包含：

- 风格总述
- 浅色主题调色板
- 深色主题调色板
- 语义颜色映射
- 阴影 / 高光配方
- 圆角与间距规则
- 组件行为说明
- 后续生成 UI 时的 do / don't 规范

该文件属于本次重设计的必交付物，不是可选文档。

## 验证策略

在本次改造被视为完成之前，至少要验证以下几点：

- 浅色和深色是否属于同一视觉家族
- 核心页面是否还有明显旧风格残留
- 任务扫描效率是否仍然足够高
- 状态可读性是否被完整保留
- 各类控件的深度反馈是否一致
- 是否还有关键页面回退成局部拼装样式

最少应执行以下验证方式：

- 基于代码的 token / 组件使用检查
- 核心页面在浅色 / 深色下的人工审视
- 条件允许时，对共享 UI 行为做必要的结构性测试或针对性验证

## 风险

- 拟物化使用过度会削弱可读性。
- 深色拟物化如果层级处理不当，容易发糊。
- 页面级全面重写范围较大，迁移过程中可能暂时出现风格不一致。
- 如果不系统清理，旧的硬编码样式可能残留。

## 风险缓解

- 始终将任务和状态可读性放在风格纯度之前。
- 对活跃态、危险态保留语义强调层。
- 先建立共享原语，再完成页面重绘。
- 在实施过程中系统清查旧颜色、旧阴影和一次性局部装饰。
